# papertrade-rust

[Papertrade](https://docs.papertrade.xyz/)（HyperEVM 上的合成永续）的双账户对冲机器人，Rust 版。两个专用账户在同一市场一多一空、等额开仓，价格偏离开仓价达到阈值（默认 100 bps）时两边一起平仓，然后重复。亏损的一边按亏损额铸造 PAPER，两边合计的净损耗就是获得 PAPER 的成本。

这是 [TypeScript 版](https://github.com/AnalyThothAI/papertrade) 的重写：策略规则相同，多了本地数据库、操作员控制和终端面板，形成"决策 → 执行 → 落账 → 可见 → 人工干预"的闭环。

> 协议没有公开 API。线路协议来自官方前端（`exchange.papertrade.xyz`）的实际行为，随时可能变化。合约是可升级代理，资金风险自负。
> 两个版本**不要同时对同一组账户运行**：它们互不知情，会各开一轮。

## 结构

```
                    ┌──────────────── papertrade run（常驻进程）────────────────┐
 账户状态流 (SSE) ─▶│                                                          │
 Hyperliquid 盘口 ─▶│  收集已知信息 ─▶ decide()（纯函数）─▶ 签名并提交意图     │─▶ 中继
 交易开关 / 队列  ─▶│        ▲                    │                            │
                    └────────│────────────────────│────────────────────────────┘
                             │ 读                 ▼ 写
                    ┌────────┴───────── data/papertrade.db（SQLite）───────────┐
                    │ control 操作员意图 │ status 实时快照 │ events 时间线      │
                    │ intents 意图预写日志 │ trades 成交台账                    │
                    └────────▲───────────────────▲─────────────────────────────┘
                             │ 写 control        │ 只读
                  pause / resume / flatten     tui · status · 任何 SQLite 工具
```

- **机器人只有一个写入方**：常驻进程。面板和命令行都通过数据库和它交互，随时可开可关，不影响交易。
- **数据库就是机器人相信的事实**：它看到什么、打算做什么、做过什么、结果如何，都能直接查。
- **意图先落盘再发送**：重启后会接着跟踪上次没有落定的意图，不会因为"不知道发没发出去"而重复开仓。

## 快速开始

```bash
cargo build --release
cp .env.example .env                       # 填入两个钱包地址
./target/release/papertrade keys init      # 设一个密码，生成并加密两把 session key；不联网
./target/release/papertrade run            # 输入一次密码。PT_DRY_RUN=true：只决策和记录，不签名、不提交
./target/release/papertrade tui            # 另开一个终端看面板，不需要密码
```

`run` 是一个普通的前台程序：开着它的终端在，它就在。想让它在你断开 SSH 后继续跑，把它放进你自己用的终端复用器（zellij、tmux、screen 都行），这部分不归本工具管。

- **它自己会恢复。** 行情或账户流断了、启动时网络不通，`run` 会在同一个进程里等 5 秒后重新开始，不需要外部看护，也不会再问密码。`Ctrl-C` 让它做完当前这一拍后退出。
- **密码只在启动时输入一次，而且只从终端输入。** 进程退出后再启动要重新输入。没有终端（管道、重定向的 stdin）时 `run` 直接拒绝启动；终端复用器里的窗口是终端，可以用。
- **随时可以重启。** 它从账户状态和意图日志接管，不依赖内存。
- **同一个数据目录只允许一个 `run`**，第二个会被拒绝。
- 面板和 `status` 在任意终端里随时开关，不影响 `run`。

`keys init` 生成的 session key（只能开/平仓，不能提现）要由账户的主钱包注册后才能用，30 天有效。本地生成不等于已注册：没注册时机器人只会等待，面板显示 `NOT REGISTERED`。

```bash
papertrade session-key new long            # 输入密码，写出注册请求；不发送任何东西
# 用主钱包对它做 EIP-712 签名，例如：
#   cast wallet sign --data --from-file secrets/<钱包>.registration.json --interactive
papertrade session-key submit long --signature 0x…   # 真实的写请求，不受 PT_DRY_RUN 影响
```

密钥怎么存、密码管什么、不防什么，见[密钥](#密钥)。

打开 `PT_WALLET_AUTOMATION` 并用 `keys init` 导入两个主钱包的私钥之后，注册和续期不用手工做，两户之间的资金也会自动调平，见[主钱包私钥签什么](#主钱包私钥签什么)和[再平衡](#再平衡)。这是可选的，默认关闭。

## 命令

| 命令 | 作用 |
|---|---|
| `keys init` | 把两个账户的密钥加密存好：设密码、生成 session key，开启 `PT_WALLET_AUTOMATION` 时导入主钱包私钥。可重复执行，只补缺的。不联网 |
| `run` | 运行机器人，启动时输入一次密码；交易未开放时只会等待，开放后自动开始 |
| `tui` | 终端面板，见[面板](#面板)；`p` 暂停/恢复，`q` 退出 |
| `status` | 把面板的内容以纯文本打印一次（机器人没在运行时显示最后一次状态和时间） |
| `pause` | 不再开新一轮；已开的一轮照常持有到目标 |
| `resume` | 恢复开仓 |
| `flatten` | 立刻平掉两个账户的所有仓位，之后不开仓，直到 `resume` |
| `session-key new <long\|short>` | 为已有的 session key 写出注册请求，交给主钱包签名；要输入密码，不发送 |
| `session-key submit <long\|short>` | 把签好的注册提交给中继。真实写请求，不受 `PT_DRY_RUN` 影响 |
| `rebalance abandon` | 结束一笔卡住（`stuck`）的转账；只改记录，不动资金，不需要密码，见[再平衡](#再平衡) |

想要网页视图，不需要额外代码：[Datasette](https://datasette.io) 可以直接把数据库变成可浏览、可查询的网站。

```bash
uvx datasette data/papertrade.db      # http://127.0.0.1:8001，表 events / intents / trades_usd
```

## 配置

命令行参数或环境变量（`.env` 会被自动读取）。

| 变量 | 默认 | 含义 |
|---|---|---|
| `PT_LONG_ACCOUNT` / `PT_SHORT_ACCOUNT` | — | 做多 / 做空账户的主钱包地址 |
| `PT_KEYS_DIR` | `./secrets` | 密钥目录，里面只有密文，见[密钥](#密钥) |
| `PT_DATA_DIR` | `./data` | 数据库目录 |
| `PT_COIN` | `BTC` | 市场 |
| `PT_NOTIONAL_USD` | `10000` | 每腿仓位价值；协议下限为 10,000 |
| `PT_LEVERAGE` | `20` | 杠杆；保证金 = 仓位价值 ÷ 杠杆 |
| `PT_CLOSE_BPS` | `100` | 平仓阈值；必须不超过强平距离的一半 |
| `PT_REQUIRE_EMPTY_QUEUE` | `true` | 仅在 LP 派彩队列为空、且两个账户都没有排队款时开仓 |
| `PT_INTENT_TTL_SECONDS` | `120` | 每个签名意图的有效期 |
| `PT_DRY_RUN` | `true` | 只决策和记录，不签名、不提交。对 `run` 里的一切写操作生效 |
| `PT_WALLET_AUTOMATION` | `false` | 是否让机器人持有并使用两个主钱包自己的私钥。关闭时不询问、不读取，目录里有文件也一样 |

密码和私钥没有对应的变量或参数：它们只从终端输入。

## 密钥

`PT_KEYS_DIR`（默认 `./secrets`，已被 `.gitignore` 忽略）里每把密钥一个文件，文件名是账户主钱包地址的小写形式：

| 文件 | 内容 | 什么时候有 |
|---|---|---|
| `<钱包>.session.json` | session key 的密文。只能为该钱包开仓、平仓 | `keys init` 生成 |
| `<钱包>.wallet.json` | 该钱包自己私钥的密文 | 仅 `PT_WALLET_AUTOMATION=true` 时，由 `keys init` 用不回显的输入导入 |
| `<钱包>.registration.json` | session key 的注册请求，只有地址和数字，没有秘密 | `session-key new` 写出 |

所有密文用同一个密码加密，各自有随机的 salt 和 IV。密码不写进任何地方：不在 `.env`、参数、数据库、日志里。**忘了密码没有后门**，备份就是复制这个目录，密码自己另外保管。

`keys init` 做的事：

- 目录里还没有密文：让你设一个新密码（输入两次，至少 16 个字符；这只是下限，不代表够强，最好用密码管理器生成的随机密码）。
- 已经有密文：问一次现有密码，先确认它能解开**每一个**已有文件，否则什么都不改就退出。
- 缺 session key 就生成一把并加密；`PT_WALLET_AUTOMATION=true` 且缺主钱包私钥时，请你输入它，并核对它推导出的地址就是配置里的那个钱包，不是就拒绝。
- 只新增文件，从不覆盖、不轮换已有的密钥。所以它可以重复执行：中途断了，或者后来才打开 `PT_WALLET_AUTOMATION`，再跑一次即可。
- 全程不联网：不注册、不提现、不转账、不下单。

`run` 怎么用它们：

- 先确认两把 session key 的密文都在，再问一次密码，解密后放在内存里，直到进程退出。之后的每一拍、每一次进程内重新开始，都用这同一份，不再读文件、不再解密。
- 缺 session key、密码错、文件损坏：明确报错后退出，不会自己生成新密钥。
- `tui`、`status`、`pause`、`resume`、`flatten` 只读写数据库，不碰密钥，不问密码。`flatten` 是让正在运行的 `run` 去平仓，不是这条命令自己去签名。

两种工作模式：

| | `PT_WALLET_AUTOMATION=false`（默认） | `PT_WALLET_AUTOMATION=true` |
|---|---|---|
| 这台机器上的密钥 | 两把 session key | 再加两个主钱包的私钥 |
| 泄露的最坏情况 | 交易余额被恶意交易亏掉；不能提现 | 钱包能做的一切 |
| 注册 session key | 人工：`session-key new` → 主钱包签名 → `session-key submit` | 机器人自己签：未注册或剩余不足 3 天时注册、续期 |
| 资金再平衡 | 人工：机器人只写明从哪边转多少 | 机器人自己做，见[再平衡](#再平衡) |

打开后某个主钱包私钥没能加载（文件缺失、损坏、不是这个钱包的），`run` 照常启动：日志给出原因，面板上该账户显示 `wallet key UNAVAILABLE`，`status` 里有完整原因。它不会用主钱包签任何东西，但 session key 仍然管理和平掉已有仓位。

> 主钱包自动化的业务（自动注册与续期、提现、Hyperliquid 转账）对模拟交易所验证过，对真实交易所一次都没有跑过，见[再平衡](#再平衡)末尾的清单。第一次打开应该用小额、有人盯着。不需要它的时候保持 `false`：那样主钱包私钥就不在这台机器上。

这套加密保护的是**落在磁盘上的文件**：备份、误提交、磁盘被拷走时，拿到文件的人还需要密码。它不保护已经解锁的进程：能读这个进程内存的程序、以同一用户运行的恶意软件、键盘记录，都不在它的防护范围内。

文件格式是标准的 Web3 Secret Storage V3，由 [alloy](https://github.com/alloy-rs/alloy)（经 `eth-keystore` 0.5.0）读写：`aes-128-ctr`，密钥由 `scrypt` 派生，N=8192、r=8、p=1。这是库的默认参数，不是本项目挑的，而且偏轻（Geth 默认 N=262144）：对弱密码的离线暴力破解几乎不设防，强度全靠密码。读取时只接受这一种格式（V3、`aes-128-ctr`、`scrypt` 且 N 在 8192 到 262144 之间），其余一律拒绝。测试把写出的文件和锁定的依赖版本钉在这组参数上，依赖升级不会悄悄换格式。

## 它如何决策

整个策略是一个纯函数 [`decide`](src/strategy/decide.rs)。每个"等待"都对应 [`Wait`](src/strategy/decide.rs) 里一个具体、可检查的原因，面板和时间线显示的就是它。

| 两条腿的状态 | 动作 |
|---|---|
| 账户状态未知 | 等待 |
| 有意图在中继排队，或刚发出不到 10 秒 | 等待 |
| `flatten` 模式 | 平掉所有仓位（包括预期之外的），不开仓 |
| 空仓 | 先看两户资金（见[再平衡](#再平衡)）：有转账未完成、资金不足或需要调平时不开仓；否则所有开仓条件满足时两腿同时开仓。`pause` 模式下等待 |
| 已对冲（两边各一个方向正确的仓位） | 偏离达到阈值时平仓，亏损腿先平 |
| 只剩一条腿 | 立刻平掉它，不需要行情 |
| 出现预期之外的仓位 | 不动，等人工处理或 `flatten` |

面板和 `status` 里的 `legs` 就是这个状态（`flat` / `hedged` / `one leg (long)` / `unexpected positions` / `unknown`）。

安全规则：

- **平不了就不开**：中继暂停平仓时不会开仓。
- **结果未知不重发开仓**：提交结果不明的开仓在链上时间越过其有效期之前都可能执行，这期间不会再开仓。判断用的是索引器报告的链上时间，不是本机时钟。
- **开仓靠证据确认，平仓可以重发**：开仓只有在仓位出现、中继报告失败或过期后才算落定，不会因为"从队列里消失了"就当它失败；平仓重复发送无害，所以无应答或被拒时会重发（每 5 秒一次，不是每个循环一次）。
- **不为一个没影的意图裸着一条腿**：一条腿已成交、另一条腿的开仓发出 10 秒后既不在中继队列里也没有结果，就先把已成交的腿平掉。
- **开仓有冷却**：每次开仓尝试后，等一个意图有效期再允许下一次，重启后仍然有效。
- **数据不新鲜就不动**：账户流中断或静默、行情超过 30 秒没更新时一律等待。账户流每 30 秒主动重连对账一次，连接失败时退避重试。
- **数据库只影响开仓**：意图日志写不进去就不开仓；平仓不依赖数据库。
- **后台任务停了就重新开始**：行情或账户流任务停了，这一轮运行结束并在 5 秒后重新启动，而不是拿着旧数据一直等。

## 主钱包私钥签什么

主钱包私钥怎么导入、怎么解锁，见[密钥](#密钥)。这里说的是解锁之后它被用来做什么。

主钱包私钥能做钱包能做的一切，所以它解锁后只放在 [`src/wallet.rs`](src/wallet.rs) 的 `WalletSigner` 里。`WalletSigner` 不向外交出签名器，只签三种东西：

| 签什么 | 用在哪 |
|---|---|
| `RegisterSessionKey`，只能是这个钱包自己的 | 注册和续期机器人的 session key |
| `WithdrawToCore`，只能是从这个钱包提 | 再平衡的第一步：提现到这个钱包自己的 HyperCore 账户 |
| Hyperliquid 上的一笔 USDC 转账，收款方是**对方账户的存入地址** | 再平衡的第二步 |

- 开仓、平仓只认已注册的 session key，主钱包私钥自己签会被合约拒绝；提现只认主钱包私钥。这是合约的规则。
- 没有"转到任意地址"的入口。转账的收款地址不是参数，而是拿对方账户的钱包地址去链上的存入地址工厂（`computeProxyAddress`）现读出来的，不采用中继返回的地址；读不到就不发。
- 某个钱包的私钥已解锁时，机器人发现它的 session key 未注册或剩余不足 3 天，会自己签 `RegisterSessionKey` 并提交：已有一笔在排队或还可能执行时不重复提交，没成功的至少隔 5 分钟再试。
- 自动再平衡需要两个钱包的私钥都已解锁。开关关着，或者有一把没能解锁（`UNAVAILABLE`），就只提示。
- `PT_DRY_RUN=true` 时这三种都不签。

## 再平衡

每一轮都有一边亏、一边赢，两户余额会越拉越开，直到亏得多的一边付不起保证金。再平衡把多的一边的钱挪一半差额到少的一边。

### 什么时候转

只在空仓、没有还可能执行的开平仓意图、模式为 `run` 时判断（[`funds`](src/strategy/rebalance.rs)，纯函数）。保证金 = 每腿仓位价值 ÷ 杠杆；缓冲 = 一轮的亏损额（仓位价值 × 平仓阈值）。默认配置下是 500 和 100。

| 条件 | 结论 |
|---|---|
| 两户可用余额都 ≥ 保证金 + 缓冲 | `enough`：照常开仓 |
| 两户合计 < 2 × 保证金 | `underfunded`：不转账、不开仓，等充值 |
| 否则，转移量 = ⌊(多的 − 少的) ÷ 2⌋，整数 USDC | 转移量 ≥ 10：`rebalance`，从多的一边转到少的一边。不足 10：不转，按各自余额够不够保证金决定能否开仓 |

- 需要调平时，两个主钱包的私钥都已解锁就发起转账；否则只等待，并写明从哪边转多少（例如 `needs a manual rebalance: move 850 USDC from the long account to the short account`），人工转完后自动继续。
- 资金判断排在所有开仓条件之前，所以中继暂停开仓期间也能先把两户调平。中继暂停 `withdrawToCore` 时不发起。
- 有转账未完成（包括卡住）时不开仓。平仓不受这一节任何规则影响。
- `PT_DRY_RUN=true` 时只显示这个决定，不发起转账，也不推进未完成的转账。

### 一笔转账怎么走

Papertrade 的资金托管在 HyperCore 上：提现只会落到提现钱包自己的 HyperCore 账户，存入只认转进专属存入地址的 USDC。所以从账户 A 到账户 B 要走三段，中间一段是 Hyperliquid 上的转账（不是交易）：

```
 withdraw ───▶ send ───▶ credit ───▶ done
     └───────────┴──────────┴──▶ stuck（需要人看一眼）
```

| 阶段 | 动作 | 完成的证据 | 没等到证据 |
|---|---|---|---|
| `withdraw` | A 的钱包私钥签 `WithdrawToCore`，经中继提交 | A 的 HyperCore USDC ≥ 基线 + 金额 | 提现还可能执行：一直等。已不可能执行（被拒、失败、过期），且 30 秒后读到的余额显示什么都没动（HyperCore 没多，Papertrade 没少）：重签，最多 3 次，然后 `stuck`。其余情况（例如中继说执行了但 HyperCore 没到）：10 分钟后 `stuck` |
| `send` | A 的钱包私钥签转账，收款方是 B 的存入地址 | A 的 HyperCore USDC ≤ 基线 − 金额 | 30 秒后读到的余额没变：视为没发出，重发，最多 3 次，然后 `stuck`。余额少了但不够金额：`stuck` |
| `credit` | 每 15 秒请中继检查一次 B 的存入地址 | B 的 Papertrade 余额 ≥ 基线 + 金额 − 1（容许 1 USDC 的激活费） | 10 分钟后 `stuck` |
| `stuck` | 停止自动处理，不开仓；面板和时间线写明卡在哪一步、钱应该在哪 | 人工处理后运行 `papertrade rebalance abandon` | — |

这个状态机是纯函数 [`next_step`](src/strategy/transfer.rs)：输入这笔转账的记录和当前观察到的余额、时间，输出下一步。循环只负责执行和落盘。它遵守这几条：

- **先落盘，再执行，凭余额确认。** 每次尝试先把时间和基线余额写进 `transfers` 表，然后才发请求。请求返回成功还是失败都不作数，只有余额变了才算完成。余额读不到就等，不猜。
- **同一时间最多一笔。** 由数据库的唯一索引保证。
- **不重复提现。** 提现和开仓一样先写意图日志：结果未知的提现，在链上时间越过它的有效期之前不重签；中继报告已执行的提现永远不重签。
- **不重复转账。** 一笔转账的每次重发都是同一个 nonce、同一份签名，而 Hyperliquid 对同一签名者的同一个 nonce 只执行一次。官方前端也是这样重发的。
- **随时可以杀掉进程。** 钱只会在三个地方之一：A 的 Papertrade 余额、A 的 HyperCore 账户、B 的存入地址。重启后按记录和余额接着走。
- **`stuck` 不会自己恢复**，即使钱后来到了。确认资金去向并处理好之后运行 `papertrade rebalance abandon`，机器人按那时的余额重新判断。

前提和还没有实盘验证的地方（第一次应以 10–20 USDC、有人盯着的方式走一遍）：

- 两个钱包在 HyperCore 上都要已经有账户。HyperCore 向第一次收款的地址收 1 USDC 激活费：提现钱包自己的 HyperCore 账户如果还不存在，到账会少 1 USDC，`withdraw` 等不到证据，10 分钟后 `stuck`，钱在这个钱包的 HyperCore 账户里。存入地址在第一次入金时已经激活过。
- 转账用哪个 Hyperliquid 动作，跟的是官方前端的存入流程：发款账户是默认模式时用 `spotSend`，是统一账户或组合保证金时用现货到现货的 `sendAsset`。请求的格式有单元测试，但没有真的发过。
- 中继是否接受机器人提交的提现意图（合约层的签名已用只读模拟确认）、`/funding/deposits/check` 的实际行为、提现到账和入账的实际耗时。30 秒和 10 分钟是保守估计，实测后调整。

## 预估

一轮的结果由协议规则决定。机器人按这些规则先算出来，写进状态快照，面板和 `status` 都显示。它回答两个问题：这一轮走到目标时大约拿多少 PAPER、花多少钱；如果现在就平仓呢。

| 输入 | 来源 | 刷新 |
|---|---|---|
| 盈利折扣的四个参数：`baseRate`、`rateMultiplier`、`referenceNotional`、`positionMultiplier` | `/state/trading` 的品种记录 | 5 秒 |
| 赢利费、亏损费、强平费 | 链上 Exchange 合约的 `winFeeRate()`、`lossFeeRate()`、`liquidationFeeRate()`（只读调用） | 30 秒 |
| 铸造曲线：`trackedLp`、`cliff`、`rate`、`decay`、`tailProgress` | `/query/protocol/summary` 的 `paper` 段 | 30 秒 |
| 派彩队列是否为空 | `/query/protocol/queue-summary` | 5 秒 |
| 开仓价、保证金、杠杆、强平价 | 已对冲时是两条腿的实际仓位；否则是当前中间价和配置的仓位（即下一轮） | 实时 |

规则都在 [`src/economics.rs`](src/economics.rs)，纯函数、整数运算：

1. **平仓估值**。死区 = 开仓价 ÷ 50000（0.2 bps）：盈利一方的平仓价先向不利方向挪一个死区，挪完不再盈利就按 0 计。盈利再乘以折扣 `(1 − baseRate) ÷ (1 + 1 ÷ (move × rateMultiplier) + referenceNotional ÷ (10⁶ × move × positionMultiplier))`，`move` 是扣掉死区后的偏离比例。亏损不打折，最多亏光保证金。这一段逐位移植自官方前端的估值函数（与合约的 `applyMarketImpact` 对应）；[`tests/fixtures/valuation-golden.json`](tests/fixtures/valuation-golden.json) 是用官方函数跑出来的对照表，测试要求每一位都相同。
2. **赢利费**。折扣后的盈利再扣 `winFeeRate`。
3. **铸造率**。`trackedLp < cliff`（包括为负）时每 1 USD 铸造基数铸 `rate` 枚；否则是 `rate × (decay ÷ (decay + tailProgress))²`。
4. **铸造基数**。派彩队列为空时平仓：亏损额减去亏损费（`亏损 × lossFeeRate`）；队列非空时平仓：全额亏损；被强平：全部保证金。

给出两组数字，每组都是亏方亏损、赢方到手、两边合计净额、预计 PAPER、每枚 PAPER 的成本：

- **到目标时（at target）**：在开仓价上方、刚好达到平仓阈值的价格两边一起平仓。两腿等额时向下走同样的距离结果相同，只是输赢互换，所以只算一个方向。空仓时这就是下一轮的预估。
- **现在平仓（now）**：按当前中间价平仓。只在已对冲且有新鲜报价时给出。

默认配置下（BTC、每腿 10,000 USD、阈值 100 bps、三项费率 2%、铸造率 100、队列为空）：亏方亏 100.00，赢方到手 86.38（死区扣掉 0.20，剩下的 99.80 保留约 88.3%，再扣 2%），净额 −13.61，铸 9,800 PAPER，每枚约 0.00139 USD。偏离越小折扣越重：走到一半（50 bps）时每枚约 0.00157 USD。

它只是预估：

- **缺输入就不给数字**。任何一项读不到或连续三次没刷新，预估整段显示为缺失，不沿用旧值，也不用 0 代替。预估只用于显示，这些输入读不到不影响开仓和平仓。
- **实际平仓价不是目标价**。平仓按落块时的中间价结算，通常比阈值再远一点。
- **没有计入的情况**：LP 现金不够时亏损费会被免除（铸造基数变成全额亏损）；一笔铸造跨过 `cliff` 时前后两段铸造率不同；`tail` 区公式在合约里的取整顺序未核对。
- **一处文档没说清的地方**：`tailProgress` 只增不减。LP 被质押者提走、`trackedLp` 回落到 `cliff` 以下之后，铸造率是回到 `rate` 还是保持衰减后的值，文档两种说法都有。这里按"`trackedLp < cliff` 就是 `rate`"处理；目前 `trackedLp` 和 `tailProgress` 都是 0，两种读法结果相同。
- **估值与链上结算是否逐位一致**，要等第一笔真实平仓来对比。铸造率和铸造基数来自官方文档，不是合约代码。

## 面板

`papertrade tui` 和 `papertrade status` 显示同样的内容，读的都是数据库里的状态快照、台账和时间线。110 列 × 40 行能完整显示。

| 区域 | 内容 |
|---|---|
| 顶栏 | 模式（`RUN` / `PAUSE` / `FLATTEN`）、是否 dry-run、机器人是否在线（快照超过 5 秒没更新即视为没在运行）、两腿状态、当前决定及原因 |
| Market | 中间价、开仓价（两腿均价）、这一轮已持有多久、偏离与进度条、两侧的平仓触发价、两条腿的强平价、派彩队列、交易是否暂停、中继拒收哪些动作 |
| Estimate | 当前铸造率、三项费率、"到目标时"与"现在平仓"两组数字，见[预估](#预估) |
| LONG / SHORT | 可用余额、排队款、session key 剩余时间（没注册显示 `NOT REGISTERED`）、主钱包私钥在这次运行里是 `loaded`、`off` 还是 `UNAVAILABLE`、在途意图数、仓位 |
| Funds | 两户合计与差额、按当前余额还能开几轮、资金结论、转账是自动还是人工；有转账时显示方向、金额、阶段、已用时间和说明（卡住时是原因） |
| Ledger | 已结算笔数、净盈亏、已得 PAPER、实际每枚成本 |
| Timeline | 决定变化、每个意图的提交结果、每笔结算、模式变更，新的在上 |

不知道的值显示为 `—`、`unknown` 或一句说明（例如 `no fresh quote`、`account state unavailable`、`no estimate: an input is missing`），不会显示成 0。平仓触发价与 [`decide`](src/strategy/decide.rs) 用的是同一条规则：中间价到达或越过它就平仓。

## 异常场景

两条腿是两个独立的意图，不是原子的。下面是每种异常下机器人的行为，以及一条腿裸露（单边持仓）的最长时间。除最后三行外，都有对应的端到端测试（[`tests/rounds.rs`](tests/rounds.rs)）。

| 场景 | 机器人的行为 | 单腿裸露上限 |
|---|---|---|
| 一条腿被中继当场拒绝 | 立刻平掉已成交的腿 | 一次中继往返 |
| 一条腿执行时失败（中继报告失败） | 同上 | 一次中继往返 |
| 一条腿的开仓无应答，实际没到中继 | 10 秒后平掉已成交的腿；该意图过期前不再开仓 | 约 10 秒 |
| 一条腿的开仓无应答，实际执行了 | 仓位出现后按正常对冲处理 | 无 |
| 一条腿在中继队列里迟迟不执行 | 等它；它最晚在有效期（默认 120 秒）到时失效 | 意图有效期 |
| 仓位比"意图离开队列"晚出现 | 10 秒内等待，不会误平另一条腿 | 无 |
| 到达目标后，某条腿的平仓无应答或被拒 | 重发平仓 | 重发间隔 |
| 一条腿被强平 | 立刻平掉另一条腿 | 一次中继往返 |
| 账户流中断 | 不动作；恢复后按实际状态处理 | 中断时长（若期间有腿被强平） |
| 行情中断 | 已对冲则继续持有；只剩一条腿时照样平 | 无 |
| 进程崩溃或重启 | 重启后从账户状态和意图日志接管，不会重复开仓 | 停机时长 |
| 数据库不可写 | 平仓照常，不开新仓 | 无 |
| 中继暂停平仓 | 不开新仓；已有仓位平不掉 | **无上限**（协议限制） |
| `run` 没在运行（终端关了、整机宕机） | 无人处理 | **无上限** |
| 强平前来不及平仓（价格在平仓落块前穿过强平线） | 亏损腿被强平，盈利腿随后被平掉 | 一次中继往返；损耗高于正常一轮 |

资金和转账的异常都发生在空仓时，没有腿会因此裸露；要看的是钱在哪。每一行都有端到端测试。

| 场景 | 机器人的行为 | 钱在哪 |
|---|---|---|
| 一户余额不够保证金加一轮亏损，两户合计够 | 两个主钱包的私钥都已解锁：转一半差额过去，到账后再开仓。否则（开关关着，或有一把是 `UNAVAILABLE`）：等待，并写明从哪边转多少 | 没动，或在转账途中 |
| 同上，但差额的一半不足 10 USDC | 不转；各自余额够保证金就照常开仓 | 没动 |
| 两户合计不足两份保证金 | 不转账、不开仓，等充值 | 没动 |
| 有仓位，或有开平仓意图还可能执行 | 不发起转账 | 没动 |
| 中继暂停 `withdrawToCore` | 不发起转账；暂停开仓不影响转账 | 没动 |
| 提现被中继拒绝 | 30 秒后确认两个余额都没动，再重签；连续 3 次不成则 `stuck` | A 的 Papertrade 余额 |
| 提现无应答，实际没到中继 | 链上时间越过它的有效期之前不重签；之后同上 | A 的 Papertrade 余额 |
| 提现无应答，实际执行了 | HyperCore 余额增加即继续，不会再签一笔 | A 的 HyperCore 账户 |
| 提现执行了，但结果通知没收到，到账又很慢 | Papertrade 余额已经少了，说明钱出去了：不重签，等它到账 | 在去 A 的 HyperCore 账户的路上 |
| 提现到账的金额不足（例如 HyperCore 扣了激活费） | 不把不够的钱转出去，也不重签；提现不可能再执行后 10 分钟 `stuck` | A 的 HyperCore 账户 |
| Hyperliquid 转账无应答，实际没发出 | 30 秒后余额没变，用同一个 nonce 重发；3 次不成则 `stuck` | A 的 HyperCore 账户 |
| Hyperliquid 转账无应答，实际发出了 | 余额减少即继续，不重发 | B 的存入地址 |
| 转账重发时第一笔其实还在处理 | 重发的是同一个 nonce，被 Hyperliquid 拒绝，只转一次 | B 的存入地址 |
| 转账后 A 的 HyperCore 余额少了，但少得不够金额 | 解释不了的变动：不当作已发出，也不重发，`stuck` | 需要人工核对 |
| 链上读不到 B 的存入地址 | 不发，也不消耗重试次数；读到后继续。不使用中继返回的地址 | A 的 HyperCore 账户 |
| 入账迟到 | 每 15 秒请中继检查一次存入地址，到账后继续 | B 的存入地址 |
| 入账比转出的少 1 USDC 以内 | 视为到账，继续 | B 的 Papertrade 余额 |
| 入账一直不来 | 10 分钟后 `stuck`，不开仓；`rebalance abandon` 之后才重新判断 | B 的存入地址 |
| 转账途中进程重启（任一阶段） | 按 `transfers` 记录和余额接着走，不重复提现，不重复转账 | 三处之一 |
| 转账途中 `pause` | 已开始的转账照常走完，不开新一轮 | — |
| 转账途中重启，这次发款钱包的私钥不可用（开关被关掉，或没能解锁） | `stuck` | 停在当时的位置 |
| session key 未注册或快到期，该钱包的私钥已解锁 | 自己注册或续期，不耽误交易；被拒后至少隔 5 分钟再试 | — |

模拟交易所是按我对线上协议的理解写的（队列版本号、结果通知、补丁内容的先后；提现到 HyperCore、存入地址被中继归集的时序）。它能证明机器人的逻辑在这些顺序下是对的，不能证明线上一定是这些顺序。第一轮实盘仍应以最小仓位、有人盯着的方式跑。

## 数据库

| 表 | 内容 |
|---|---|
| `control` | 操作员意图：`run` / `pause` / `flatten`，一行 |
| `status` | 机器人当前看到和打算做的事（JSON 快照），约每秒重写，一行 |
| `events` | 时间线：每次决策变化、每个意图的提交结果、每笔结算、每次模式变更、转账的每一步 |
| `intents` | 意图预写日志：请求原文、有效期、状态（`signed → accepted / rejected / unknown → settled`）、中继报告的结果。开仓、平仓、提现、session key 注册都在这里 |
| `transfers` | 两户之间的转账，一笔一行：方向、金额、阶段、尝试次数与时间、各阶段的基线余额、提现意图、Hyperliquid 转账的 nonce、卡住的原因。未完成的最多一行 |
| `trades` | 已结算仓位台账，来自账户成交历史；金额为精确的 18 位小数字符串 |
| `trades_usd`（视图） | 台账的浮点数版本，供显示、SQL 汇总和看板使用，不用于记账。净盈亏：被强平的仓位记负的全部保证金，其余记"折扣后盈亏 − 用户支付的手续费" |

## 组件

优先用成熟的开源库，没有自己实现协议栈之外的东西。

| 用途 | 选择 | 原因 |
|---|---|---|
| Hyperliquid 行情、余额与转账 | [`hypersdk`](https://github.com/infinitefield/hypersdk) | 在维护，基于 alloy，自带断线重连和重新订阅，转账动作的 EIP-712 签名也由它生成；官方 `hyperliquid_rust_sdk` 仍依赖已停止维护的 ethers |
| EIP-712 签名 | [`alloy`](https://github.com/alloy-rs/alloy) | `sol!` 直接从结构体定义生成类型哈希；hypersdk 也用它，不引入第二套密码学 |
| HTTP / SSE | `reqwest` + [`eventsource-stream`](https://crates.io/crates/eventsource-stream) | 账户流需要自己控制重连和定时对账，只用解析器即可；`reqwest-eventsource` 还停在 reqwest 0.12 |
| 数据库 | [`sqlx`](https://github.com/launchbadge/sqlx)（SQLite，WAL） | 异步、自带迁移；WAL 让面板在机器人写入时照常读取 |
| 终端面板 | [`ratatui`](https://ratatui.rs) + `crossterm` | 单个二进制、走 SSH 就能看、不暴露端口 |
| 网页视图 | [Datasette](https://datasette.io)（可选，外部工具） | 现成的 SQLite 网页界面，不值得为两个账户自己写前后端 |
| 命令行与配置 | `clap`（含环境变量）+ `dotenvy` | 参数、环境变量、`.env` 一套定义 |
| 密钥加密 | `alloy` 的 keystore（`eth-keystore`）+ [`rpassword`](https://crates.io/crates/rpassword) + [`zeroize`](https://crates.io/crates/zeroize) | 标准 V3 格式，不自己写密码算法；不回显的终端输入；存过密码或私钥的缓冲区用完即清 |
| 日志与错误 | `tracing`、`anyhow`、`thiserror` | 生态标准 |

## 与 TypeScript 版的对照

| | TypeScript 版 | Rust 版 |
|---|---|---|
| 策略规则 | 相同 | 相同，另加 `pause` / `flatten` |
| 签名 | viem | alloy；测试里用同一把测试密钥验证两边请求体与意图 ID 逐字节一致 |
| 状态 | 无持久化，全部从账户状态推导 | 同样推导决策；另把意图、事件、成交写入 SQLite |
| 重启安全 | 启动后等一个意图有效期再开仓 | 从预写日志恢复在途意图，无需等待 |
| 单腿裸露 | 另一条腿无应答时等到它过期（最长约 150 秒） | 10 秒后平掉已成交的腿 |
| 端到端测试 | 无 | 模拟交易所 + 75 个场景 |
| 密钥存放 | 明文文件 | 加密文件，启动时输入一次密码；两个版本的密钥目录不通用 |
| 资金调拨 | 人工 | 打开 `PT_WALLET_AUTOMATION` 后自动注册 session key、自动再平衡；否则提示人工 |
| 可见性 | 日志 + `status` 命令 | 终端面板、`status`、时间线、台账、任意 SQLite 工具 |
| 人工干预 | 停进程 | `pause` / `resume` / `flatten` |
| 部署 | Node 24 + `node_modules` | 单个二进制 |

## 已知限制

- **平仓只能走中继**。合约不接受用户直接开/平仓；持仓期间若中继暂停平仓，一条腿可能被强平而另一条腿无法关闭。`flatten` 同样受此限制。
- **盈利可能排队**。LP 付不出时，盈利部分进入 FIFO 派彩队列。
- **两腿不是原子的**，可能落在不同区块，也可能只成功一条（随后被立即平掉）。
- **再平衡没有实盘验证过**。逻辑对模拟交易所验证，提现签名对线上合约做过只读模拟；真实的提现、Hyperliquid 转账、入账一次都没有发生过，见[再平衡](#再平衡)末尾的清单。主钱包私钥没有解锁时不会自动调拨，只提示。
- **转账途中循环会等请求返回**。转账的每个请求都在主循环里发出，单个请求最长等 10 秒。转账只在空仓时进行，平仓的决定总是先于转账执行，但下一拍会被这次等待推迟。
- 截至 2026-10-10，交易尚未开放（中继暂停 `openPosition` 与 `closePositions`）。session key 注册已对线上中继验证；开仓、平仓、成交台账的字段要等开放后才能端到端确认。台账的净盈亏口径（被强平记负的保证金，其余记"折扣后盈亏 − 用户支付的手续费"）与官方前端相同，但成交记录里各字段的实际取值还没有真实数据可以核对。
